

## 一、目标与应用场景

本次验证面向 GLM-5.3 INT8 在 Kubernetes 环境中的弹性扩容、故障恢复和滚动升级场景。

部署架构：

- 推理框架：Dynamo + TensorRT-LLM
- 部署模式：1P1D Prefill/Decode 分离
- 并行配置：TP=16
- 模型：GLM-5.3 INT8
- 权重分发：ModelExpress + NIXL/UCX RDMA
- 元数据后端：Kubernetes `ModelMetadata` CRD
- 单 rank 权重数据量：约 69.32 GB

传统扩容流程：

```text
共享存储/PVC
  → 新 Pod 读取原始权重
  → 模型构造、量化配置解析、权重加载
  → 写入 PPU 显存
  → Pod Ready
```

ModelExpress P2P 流程：

```text
已运行 Source Pod 的 PPU 显存
  → NIXL / UCX / RDMA
  → 新 Target Pod 的 PPU 显存
  → Pod Ready
```

核心价值是跳过共享存储读取和大部分重复权重加载过程，降低扩容启动时间及存储 I/O 压力。

## 二、ModelExpress 仓库与组件关系

### 2.1 官方源码仓库

ModelExpress 官方仓库：

```text
https://github.com/ai-dynamo/modelexpress
```

本次使用的本地源码目录：

```text
/intern/users/yanyihui.yyh/modelexpress
```

仓库主要提供：

- MX Server；
- Kubernetes CRD；
- Python Client；
- TensorRT-LLM、vLLM、SGLang 等引擎适配；
- NIXL/RDMA 传输、元数据发布和 source 查询能力。

### 2.2 Server 与 Client 的关系

```text
                    Kubernetes API
                         │
                ModelMetadata CRD
                         │
┌────────────────────────┴────────────────────────┐
│                 MX Server                         │
│  - 元数据登记、查询、source 健康管理             │
│  - 不传输大模型权重                              │
│  - gRPC：modelexpress-server:8001                │
└───────────────┬───────────────────┬──────────────┘
                │                   │
      注册 source 元数据        查询可用 source
                │                   │
┌───────────────▼───┐         ┌─────▼────────────────┐
│ Source Worker Pod │         │ Target Worker Pod     │
│ 已加载模型权重   │         │ 新扩容的 Decode Pod   │
│ PPU 显存         │──RDMA──▶│ PPU 显存              │
│ NIXL Agent       │         │ NIXL Agent            │
└───────────────────┘         └──────────────────────┘
```

职责划分：

| 组件 | 职责 |
|---|---|
| MX Server | 管理模型 source 元数据，向新 Pod 返回可用 source 信息 |
| Kubernetes CRD | 持久化 `ModelMetadata`、`ModelCacheEntry` 等 MX 元数据 |
| MX Client | 运行在 Prefill/Decode Worker 镜像内，负责发现、注册、拉取和发布 |
| TensorRT-LLM | 通过 `checkpoint_format: MX` 启用 MX 权重加载路径 |
| NIXL/UCX | 提供跨 Pod、跨节点的 RDMA 内存传输 |
| Source Pod | 已加载模型的 Pod，对外提供显存中的权重 |
| Target Pod | 新建 Pod，通过 RDMA 拉取 source 权重 |

MX Server 是控制面和注册中心；真正的 69 GB 级权重数据不会经过 MX Server，而是由 Source 与 Target Pod 直接通过 RDMA 传输。

## 三、实施与配置流程

### 3.1 安装 CRD

在目标 Kubernetes 集群中注册 ModelExpress CRD：

```bash
kpp apply -f /intern/users/yanyihui.yyh/modelexpress/helm/crds/modelexpress-crds.yaml
```

验证：

```bash
kpp get crd modelmetadatas.modelexpress.nvidia.com
kpp get crd modelcacheentries.modelexpress.nvidia.com
```

CRD 必须先于 MX Server 和 Worker 部署，否则 MX Server 无法将 source 元数据写入 Kubernetes。

### 3.2 部署 MX Server

MX Server 部署在 `foundation` namespace，通过 Service 对 Worker 暴露：

```text
modelexpress-server.foundation.svc.cluster.local:8001
```

验证：

```bash
kpp get pods -n foundation -l app=modelexpress-server
kpp get svc -n foundation modelexpress-server
kpp logs -n foundation -l app=modelexpress-server --tail=50
```

预期日志：

```text
Connected to Kubernetes, using namespace 'foundation'
Starting gRPC server on: 0.0.0.0:8001
```

### 3.3 构建 Worker Client 镜像

Worker 镜像基于 Holmes，并加入与当前 TRT-LLM 兼容的 ModelExpress Client。

本次验证发现 Holmes 当前 TRT-LLM 原生 MX Loader 与 MX Client `v0.5.0` 接口匹配；MX Client `v0.5.1` 的模块结构变更会导致加载路径无法正确发布权重元数据。

最终 Worker 镜像需同时包含：

```text
Holmes / PPU SDK
+ TensorRT-LLM
+ NIXL Python binding
+ ModelExpress Client v0.5.0
```

### 3.4 Engine 参数配置

文件：

```text
apps/hllm/glm-5dot3/overlays/pprod/configmap-engine-args.yaml
```

在 Prefill、Decode 引擎参数中均配置：

```yaml
checkpoint_format: MX
mx_config:
  server_url: modelexpress-server.foundation.svc.cluster.local:8001
```

### 3.5 DGD Worker 环境变量

文件：

```text
apps/hllm/glm-5dot3/overlays/pprod/deploy-1p1d.yaml
```

Prefill、Decode 的 `envs` 中统一配置：

```yaml
- name: MODEL_EXPRESS_URL
  value: "modelexpress-server.foundation.svc.cluster.local:8001"

- name: MX_SERVER_ADDRESS
  value: "modelexpress-server.foundation.svc.cluster.local:8001"

- name: MODEL_NAME
  value: "GLM-5.3-Quant-W-INT8-PerChannel-A-INT8-PerToken"

- name: MX_RDMA_NIC_PIN
  value: "off"

- name: MX_POOL_REG
  value: "0"

- name: MX_VMM_ARENA
  value: "0"

- name: UCX_RNDV_THRESH
  value: "0"
```

其中 `MODEL_NAME` 必须在 Source 和 Target 端完全一致。它参与 source 身份匹配；若 Source 使用完整 checkpoint 名称、Target 使用 `GLM-5.3` 短名称，则无法发现可用 source。

对外推理服务模型名仍可保留：

```text
DYN_MODEL_NAME=GLM-5.3
```

二者职责不同：

| 变量 | 用途 |
|---|---|
| `MODEL_NAME` | ModelExpress source 身份和 P2P 匹配 |
| `DYN_MODEL_NAME` | Dynamo 对外 API 暴露的模型名 |

## 四、验证流程

### 4.1 首 Pod：磁盘加载与 source 注册

1. 保持 Prefill、Decode 初始副本数为 `1`。
2. 首个 Worker 没有可用 source，自动从磁盘/PVC 加载权重。
3. 加载完成后，向 MX Server 发布 `ModelMetadata`。
4. 验证元数据：

```bash
kpp get modelmetadatas -A
```

只有看到对应模型的 `ModelMetadata`，才说明后续 Target Pod 可发现 Source。

### 4.2 第二个 Decode：P2P RDMA 验证

1. 扩容 Decode 至两个副本。
2. 新 Decode Pod 查询 MX Server。
3. MX Server 返回已有 Source。
4. Target Pod 通过 NIXL/UCX RDMA 从 Source 显存拉取权重。
5. 检查 Target 的 rank 日志。

关键命令示例：

```bash
kpp -n app exec <NEW_DECODE_POD> -c main -- \
  sh -c 'grep -h "Found source\|Target has\|Transfer\|fallback" /tmp/mx_logs/rank0.log'
```

成功标志：

```text
Found source: ...
Target has ... params on GPU 0
Transfer complete: ...
```

## 五、实验结果

### 5.1 无 P2P 磁盘加载基线

| 指标 | 结果 |
|---|---:|
| 纯磁盘权重加载 | 约 371 秒 |
| `Model init total` | 约 455 秒 |
| 扣除 30 秒 MX source 查询等待后初始化基线 | 约 425 秒 |

### 5.2 P2P RDMA 扩容结果

关键日志：

```text
Found source: 32 workers
Transfer complete: 1941 tensors, 69.32 GB in 8.36s (66.4 Gbps)
Model init total -- 63.205
```

| 指标 | 结果 |
|---|---:|
| P2P 传输张量数 | 1941 |
| P2P 传输数据量 | 69.32 GB |
| P2P 传输时间 | 8.36 秒 |
| P2P 吞吐 | 66.4 Gbps |
| `Model init total` | 63.205 秒 |

`Found source: 32 workers` 表示 Target 成功发现可用 source worker 集合；实际权重数据传输未经过 MX Server，而是 Source/Target Worker 之间直接完成。

### 5.3 性能收益

| 对比项 | 无 P2P | P2P | 提升 |
|---|---:|---:|---:|
| 权重搬运耗时 | 371 秒 | 8.36 秒 | 约 44.4 倍 |
| 模型初始化耗时 | 425 秒 | 63.205 秒 | 约 6.72 倍 |
| 初始化耗时下降 | — | — | 约 85.1% |

计算方式：

```text
权重搬运加速倍数 = 371 / 8.36 ≈ 44.4

初始化加速倍数 = 425 / 63.205 ≈ 6.72

初始化耗时下降比例 = (425 - 63.205) / 425 ≈ 85.1%
```

需注意：

- `8.36 秒` 是纯 P2P 权重传输时间；
- `63.205 秒` 是完整模型初始化时间；
- 完整初始化还包含模型构造、通信初始化、部分张量处理和 Ready 前置流程，因此不能将纯传输时间与完整初始化时间混为同一指标。

## 六、问题、限制与风险

### 6.1 部分张量走 PVC fallback

日志显示：

```text
Loading 76 size-mismatched tensors from PVC fallback
Still missing after PVC fallback
```

数据关系：

```text
1941 个 P2P 张量
+ 76 个尺寸不匹配张量
= 2017 个目标张量
```

这些尺寸不匹配张量主要为 scaling-factor 类型。说明主权重 P2P 传输已成功，但仍存在少量辅助张量未完全通过 P2P 或 PVC fallback 恢复。

因此当前结论应定义为：

> **P2P RDMA 权重传输能力和性能已验证成功；模型完整正确性、推理稳定性及少量 scaling-factor 张量兼容性仍需进一步验证。**

### 6.2 元数据生命周期

当前 TRT-LLM v0.5.0 集成产生的部分 `ModelMetadata` 状态可能为 `Unknown`，现有 reaper 无法完全自动回收，历史元数据可能积累并影响 source 选择。

测试前清理：

```bash
kpp -n foundation delete mxmeta --all
```

关联 ConfigMap 可通过 `ownerReference` 自动回收。

### 6.3 适用边界

P2P 需要至少一个可用 Source，因此：

| 场景 | 是否适用 P2P |
|---|---|
| 首次冷启动 | 否，走磁盘加载 |
| 全量重启且无存活实例 | 否，走磁盘加载 |
| 增量扩容 | 是 |
| 单实例故障恢复 | 是，前提是存在其他 Source |
| 滚动升级 | 是，前提是旧副本仍存活 |
| 多副本弹性扩缩容 | 是 |

## 七、结论

ModelExpress P2P RDMA 权重分发已在 GLM-5.3 INT8、TP=16、1P1D Dynamo + TensorRT-LLM 部署中完成验证。

新 Decode Pod 成功发现 Source，并通过 NIXL/UCX RDMA 在约 `8.36 秒` 内传输 `69.32 GB` 权重，吞吐达到 `66.4 Gbps`。

相较传统磁盘加载：

- 权重搬运速度提升约 `44.4 倍`；
- 完整模型初始化提升约 `6.72 倍`；
- 初始化耗时降低约 `85.1%`。

该方案可显著改善已有 Source 场景下的弹性扩容、故障恢复和滚动升级效率，并降低共享存储并发读取压力。

后续重点是完成 scaling-factor 张量兼容性、模型推理正确性验证，以及 `ModelMetadata` 健康检查与自动回收机制完善。
