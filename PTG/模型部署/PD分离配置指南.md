# PD 分离配置指南

> 核心结论：**P/D 配比不是固定值，而是工作负载的函数**。Prefill 消耗由"未缓存输入 Token"决定，Decode 消耗由"输出 Token"决定；任何固定配比（如 4P+2D、"6 台一个 Cell"）都无法同时适配代码、短问答、长文三类负载，必须按工作负载重新计算。

---

## 一、为什么配比必须按工作负载重算

| 阶段 | 消耗取决于 | 记号 |
|---|---|---|
| Prefill（P 侧） | **未缓存输入 Token**（缓存命中的部分不消耗 Prefill 计算） | $I_{miss}$ |
| Decode（D 侧） | **输出 Token** | $O$ |

不同负载的 $(I_{miss}, O)$ 差异巨大：

- **代码 Agent**：20K 未命中输入 + 60K 缓存命中 + 4K 输出 → 重 Prefill 上下文、长 Decode；
- **办公短问答**：2K 输入 + 500 输出 → 轻 Prefill、轻 Decode；
- **办公长文**：2K 输入 + 1K 输出 → 轻 Prefill、相对重 Decode。

同一套池子在三种负载下的平衡点完全不同，因此**固定 4P+2D 或"6 台一个 Cell"无法同时适配代码、短问答和长文**，每个生产池都要单独推导配比。

## 二、P/D 平衡配比推导公式

![[Pasted image 20261014142332.png]]

**平衡条件**：P 侧与 D 侧的请求处理能力（req/s）相等：

$$N_P \times \frac{TPS_P}{I_{miss}} = N_D \times \frac{TPS_D}{O} \;\;\Rightarrow\;\; \frac{N_P}{N_D} = \frac{TPS_D \times I_{miss}}{TPS_P \times O}$$

**符号说明**：

| 符号 | 含义 |
|---|---|
| $N_P$ / $N_D$ | Prefill / Decode 侧节点（实例）数 |
| $TPS_P$ / $TPS_D$ | 该工作负载下单节点 Prefill / Decode 吞吐（token/s，两侧口径一致即可） |
| $I_{miss}$ | 单请求**未缓存**输入 Token 数 |
| $O$ | 单请求输出 Token 数 |

**部署余量原则**：实际部署时 **D 侧留 5%~10% 余量**，确保 **P 侧为瓶颈**、Decode 时延不恶化（符合 **SLO Goodput 原则**）——P 侧吃饱时 D 侧仍有空余算力，KV 迁移与解码不排队，TPOT 不抖动。

## 三、词元工厂生产场景 P/D 平衡设计（表 3）

| 场景 | 生产池分配 | 计算工作量 / 请求 | SLA 技术请求率 | 设计含义 |
|---|---|---|---|---|
| 代码 Agent | 40P+80D | 20K 未命中输入 + 60K 缓存命中 + 4K 输出 | 30 req/s | P/D 平衡；缓存命中 60K 仅按低价计费 |
| 办公短问答 | 28P+92D | 2K 输入 + 500 输出 | 420 req/s | 基准唯一全成本盈利文本负载 |
| 办公长文 | 16P+104D | 2K 输入 + 1K 输出 | 239.2 req/s | Decode 约束增强；现金为正、全成本微利 |
| 文生图 | 不使用 LLM P/D（960 张生产 GPU 并行） | — | 64 图/s（15 s/图） | 独立图像模型池 |

**读表要点**：

1. **总池恒定**：三个文本场景的生产池总量一致（40+80 = 28+92 = 16+104 = 120 节点，即 960 张 8 卡 GPU），变化的只是 P/D 切分比例；文生图则整体占用 960 张生产 GPU 的独立图像模型池，不复用 LLM P/D 池。
2. **SLA 技术请求率 = min(P 侧能力, D 侧能力)**，即瓶颈侧的容量（验算见下节）。
3. **缓存命中是毛利来源**：代码 Agent 的 60K 缓存命中 Token 不消耗 Prefill 计算、但按低价计费，命中率越高毛利越好——这要求 P 侧必须开启 prefix/radix cache（参见 [[DeepSeek-Flash-0731 SGLang 的PD分离部署]] 中去掉 `--disable-radix-cache` 的调优）。

## 四、验算：用公式复核表 3 的配比与 SLA

单节点吞吐随上下文长度变化，必须**按负载实测**：

- 基准（短上下文）：$TPS_P = 30K$ token/s，$TPS_D = 2.3K$ token/s；
- 代码 Agent（20K 未命中 + 60K 缓存上下文）：$TPS_P$ 降至 15K，$TPS_D$ 降至 1.5K。

代入平衡公式与能力公式（P 侧能力 $= N_P \times TPS_P / I_{miss}$，D 侧能力 $= N_D \times TPS_D / O$）：

| 场景 | $TPS_P / TPS_D$ | 平衡配比 $N_P/N_D$ | 表 3 分配 | P 侧能力 | D 侧能力 | SLA = min | 瓶颈侧 |
|---|---|---|---|---|---|---|---|
| 代码 Agent | 15K / 1.5K | $(1.5K \times 20K)/(15K \times 4K)=0.50$ | 40P+80D | $40 \times 15K/20K = 30$ req/s | $80 \times 1.5K/4K = 30$ req/s | 30 req/s | 恰好平衡 |
| 办公短问答 | 30K / 2.3K | $(2.3K \times 2K)/(30K \times 500)\approx0.307$ | 28P+92D | $28 \times 30K/2K = 420$ req/s | $92 \times 2.3K/500 = 423.2$ req/s | 420 req/s | P（D 留余量） |
| 办公长文 | 30K / 2.3K | $(2.3K \times 2K)/(30K \times 1K)\approx0.153$ | 16P+104D | $16 \times 30K/2K = 240$ req/s | $104 \times 2.3K/1K = 239.2$ req/s | 239.2 req/s | D（Decode 约束增强） |

结论：表 3 的三组分配与 SLA 数字均可由平衡公式精确复现（120 节点总池下取整），可作为配置模板直接套用。

### 代码 Agent 场景吞吐下降说明

代码 Agent 的 P 吞吐从 30K 降至 15K、D 吞吐从 2.3K 降至 1.5K，原因是 **20K 未命中输入 + 60K 缓存上下文导致 KVCache 体积增大、Attention 计算量增加，有效吞吐自然下降**。注意两点：

1. **吞吐必须按真实上下文实测**，用短上下文的名义吞吐套公式会严重高估 P 侧能力、把配比算偏；
2. **缓存命中的 60K Token 不消耗 Prefill 计算，但仍按低价计费**——即 $I_{miss}$ 只计未命中部分，这正是公式中以 $I_{miss}$（而非总输入）作为 P 侧工作量的原因。

## 五、配置流程（Checklist）

1. **画像工作负载**：统计单请求 $I_{miss}$（扣除缓存命中后的输入）、$O$（输出）、目标请求率；多负载混合时按池拆分，一池一画像。
2. **实测单节点吞吐**：在该负载的真实上下文长度下压测 $TPS_P$、$TPS_D$（长上下文会显著拉低两者，见上节）。
3. **算平衡配比**：$N_P/N_D = (TPS_D \times I_{miss})/(TPS_P \times O)$。
4. **定池求解**：固定总节点数 $N = N_P + N_D$，解出 $N_P = N \times \frac{r}{1+r}$（$r$ 为平衡配比），取整。
5. **D 侧加余量**：在平衡点基础上让 D 侧能力高出 5%~10%（即从 P 侧挪 1~2 个节点到 D 侧），保证 P 为瓶颈、Decode 时延不恶化（SLO Goodput）。
6. **验算 SLA**：$SLA = \min(N_P \times TPS_P / I_{miss},\; N_D \times TPS_D / O)$，与业务目标请求率对比；不达标则扩总池而非改配比。
7. **上线后监控回调**：观察 P/D 队列深度、TTFT、TPOT。若 D 侧排队（TPOT 上升）说明 D 余量不足、P 不再是唯一瓶颈，回退一步重新分配；若 P 侧排队而 D 侧空闲过多，则余量过大、浪费算力。
8. **缓存联动**：P 侧开启 radix/prefix cache 并监控命中率——命中率上升会同时降低 $I_{miss}$（改变平衡点）并提升毛利，配比需随之复核。
