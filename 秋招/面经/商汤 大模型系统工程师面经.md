# 商汤 大模型系统工程师面经
> **岗位**：大模型系统工程师（推理部署方向）

## Q1 用的什么卡部署 Kimi-2.6？显存是多少？

我们使用的是平头哥自研的 PPU 真武 810E，单卡显存 96GB（HBM）。Kimi-K2.6 是 MoE 架构模型，采用 W4A8 量化后，模型参数本身可以压缩到单机可容纳的规模，但由于 MoE 模型的 Expert 数量多、激活参数量大，仍然需要多卡多机部署。最终生产配置是 48 卡 Prefill + 32 卡 Decode，共 80 张 PPU 卡。

## Q2 针对这种显存大、算力低的机器做了哪些针对性优化？

![[Pasted image 20260824113422.png|785]]

- **W4A8 量化**：权重量化到 4bit，激活量化到 8bit，大幅降低计算量，让 compute-bound 的 GEMM 变得更轻量；
- **PD 分离**：将 Prefill（compute-intensive）和 Decode（memory-bound）拆分到不同节点，让 Decode 阶段充分利用 PPU 的高显存带宽优势，而 Prefill 节点通过增加卡数弥补算力不足；
- **DeepEP（Expert Parallelism）**：MoE 模型的 Expert 分布式并行，减少单卡计算负载；
- **DP Attention**：Decode 阶段使用 Data Parallelism on Attention，将 KV Cache 分摊到多卡，减少单卡显存压力的同时提高带宽利用率；
- **CUDA Graph**：减少 kernel launch overhead，对算力低的硬件尤其重要——因为计算快了之后 launch 开销占比会更突出；
- **Chunked Prefill**：将长 prompt 切块，避免单次计算量过大导致延迟激增。

## Q3 了解 SGLang 吗？有看过源码吗？

了解，我在平头哥的工作主要就是基于 SGLang 做 PD 分离部署。看过源码，主要关注以下几个模块：

- **Scheduler**（`python/sglang/srt/managers/scheduler.py`）：调度逻辑，包括 waiting queue → running batch 的选择策略、preemption 机制；
- **TokenizerManager / DetokenizerManager**：前后处理的异步管道；
- **ModelRunner**（`python/sglang/srt/model_executor/`）：模型执行层，包括 forward pass、cuda graph capture/replay；
- **Memory Pool / KV Cache Manager**（`python/sglang/srt/mem_cache/`）：RadixTree-based prefix caching、block 分配与引用计数；
- **Router**（`python/sglang/srt/router/`）：多 worker 间的负载均衡与路由策略；
- **PD 分离相关**：Mooncake transfer engine 的集成，KV Cache 跨节点传输的序列化/反序列化。

我还在部署过程中修复过一些兼容性问题，比如 FA3 后端在 PPU 上的适配、RDMA 传输参数的调整等。

## Q4 SGLang 是怎么管理 full tensor 和 linear tensor 的？有什么区别？

在 SGLang 的显存管理中，这两类 tensor 的管理方式不同：

- **Full Tensor（如 KV Cache）**：采用 **block-based paged memory** 管理。KV Cache 被切分为固定大小的 block（如 16 tokens/block），通过 block table 维护逻辑到物理的映射，支持动态分配、释放、copy-on-write 和 prefix sharing。这是 PagedAttention 的核心机制。
- **Linear Tensor（如模型权重、中间激活）**：这些是**静态分配或栈式分配**。模型权重在加载时一次性分配固定显存；中间激活（forward pass 中的临时 tensor）通常使用 PyTorch 的 memory allocator 或预分配的 buffer pool，生命周期与单次 forward 对齐，用完即释放。

**核心区别：**

- KV Cache 需要跨 step 持久化、动态增长/收缩、支持 preemption（swap out），所以需要精细的 block 级管理；
- 权重是只读常量，激活是短生命周期临时变量，都不需要 paging 机制。

> [!tip] 两级映射
> SGLang 的 `ReqToTokenPool` 和 `TokenToKVPool` 分别管理 request-level 的 token 索引和实际的 KV tensor 存储，形成两级映射。

## Q5 调整 PD 分离配比的时候是怎么确定的？做了哪些测试？最看重哪个指标？

我们从 **1P1D → 2P1D → 3P2D** 逐步压测确定的，过程如下：

**测试方法：**

1. 固定输入分布（线上真实 prompt 长度分布，如 avg 2K tokens、P99 8K tokens）；
2. 逐步增加 QPS，观察各指标变化；
3. 调整 P:D 卡数比例，对比相同 QPS 下的服务质量。

**关键指标（优先级从高到低）：**

1. **TTFT（Time To First Token）**：最看重这个，直接影响用户体感。P99 TTFT 是 SLA 的硬约束；
2. **TPOT（Time Per Output Token）**：决定生成流畅度；
3. **吞吐（tokens/s per GPU）**：资源利用率；
4. **KV Cache 利用率**：Decode 侧显存是否打满。

**确定逻辑：**

- 1P1D 时 Prefill 是瓶颈（TTFT 高），增加 P 节点；
- 2P1D 时 Decode 侧 KV Cache 打满导致排队，增加 D 节点；
- 3P2D 时 TTFT P99 < 2s，TPOT < 50ms，GPU 利用率 > 70%，达到 SLA 要求；
- 最终配置 48 卡 Prefill + 32 卡 Decode（每机 8 卡，6 台 P 机器 + 4 台 D 机器）。

## Q6 有没有严格的 bound line？

有的，我们会区分 **Prefill-bound** 和 **Decode-bound** 两种状态：

- **Prefill-bound**：表现为 TTFT 升高、P 节点 GPU 利用率 > 90%、D 节点有空闲；此时应增加 P 节点或开启 chunked prefill 分摊；
- **Decode-bound**：表现为 TPOT 升高、D 节点 KV Cache 占用 > 85%、Decode 队列堆积；此时应增加 D 节点。

**判断标准：**

- KV Cache 利用率 > 85% 视为 Decode-bound 预警线；
- TTFT P99 超过 SLA（如 2s）视为 Prefill-bound；
- 实际中 MoE 模型由于 Expert 路由不均匀，还存在局部 Expert-bound 的情况，需要观察 DeepEP 通信开销。

不过实际线上流量有波动，不是严格的二分状态，更多是通过监控动态判断当前瓶颈在哪一侧，这也是我们推进 Dynamo 动态调度的原因之一。

## Q7 MTP step 等参数是怎么设置的？

MTP（Multi-Token Prediction）相关参数设置：

- **MTP steps = 1**（即额外预测 1 个 token，总共 speculate 2 个）：Kimi-K2.6 模型本身训练时带了 MTP head，我们直接用模型自带的 draft head，不需要额外的 draft model；
- **为什么不设更大**：MTP step 增大后验证阶段的计算量增加（需要验证多个 token），在 PPU 算力有限的情况下，step=1 的 acceptance rate 约 70-80%，收益/开销比最优；step=2 时 acceptance rate 下降到 50% 左右，反而不如 step=1；
- **相关参数**：
    - `--speculative-algorithm eagle`（或 medusa，取决于模型支持）；
    - `--num-speculative-tokens 1`；
    - `--speculative-draft-tensor-parallel-size` 与主模型对齐。

> [!tip] 调参依据
> 实际调参是通过 benchmark 对比不同 step 下的 effective throughput（考虑 rejection 后的有效生成速率）来确定的。

## Q8 P 阶段和 D 阶段分别开了哪些并行策略？

| 并行策略 | Prefill 阶段 | Decode 阶段 |
| --- | --- | --- |
| **Tensor Parallelism (TP)** | TP=8（单机 8 卡） | TP=8（单机 8 卡） |
| **Expert Parallelism (EP)** | DeepEP，Expert 分布在 TP group 内 | 同 Prefill |
| **Data Parallelism (DP)** | DP across machines（6 台 P 机器） | **DP Attention**（KV Cache 按 head 分片） |
| **Pipeline Parallelism (PP)** | 未开启（增加 TTFT 延迟） | 未开启 |
| **Sequence Parallelism** | 配合 TP 开启（减少激活显存） | 不需要（decode 单 token） |

**关键设计考量：**

- Prefill 阶段是 compute-bound，用 TP 分摊大 GEMM；
- Decode 阶段是 memory-bound，用 DP Attention 让每张卡只存部分 KV Cache heads，增大 batch size 提高吞吐；
- PP 不适合在线服务场景，会增加 pipeline bubble 导致延迟不可控；
- DeepEP 两阶段都开，因为 MoE 的 Expert 数量大（Kimi-K2.6 有几百个 Expert），单卡放不下。

## Q10 内部算子有支持 Triton 这种吗？对 TensorRT 和 Triton 有接触吗？

**内部算子情况：**

- 平头哥 PPU 有自研算子库（类似 CUDA kernel library），核心算子（GEMM、FlashAttention、RMSNorm、RotaryEmbedding 等）是用自研编译器 + 低级 IR 写的，不直接用 Triton；
- 但 PPU 的编程模型在设计上参考了 Triton 的 tile-based 编程范式，有类似的 block-level parallelism 抽象；
- 对于一些非关键路径的算子，支持 Python fallback 或者通过 Triton-like DSL 快速原型验证。

**个人接触：**

- **Triton**：了解其编程模型（`tl.load/store`、grid/block 的映射），在 Mini-vLLM 项目中参考过 FlashAttention 的 Triton 实现来理解 tiling 策略；
- **TensorRT**：在 OPPO 实习时有间接接触，OPPO 的端侧部署最终会走 TensorRT/自研推理框架，我负责的量化部分需要确保 scale/zp 格式与后端 engine 兼容；
- 我对 Triton 的 auto-tuning 机制（`triton.autotune`）和 TensorRT 的 layer fusion/kernel selection 流程有概念性了解，但没有深度参与底层 kernel 开发。

## Q11 量化的粒度是什么？per channel or per tensor？

**Kimi-K2.6（W4A8）的量化粒度：**

- **权重（W4）**：**Per-group quantization**，group size = 128。即每 128 个连续权重元素共享一组 scale/zero_point。这是 GPTQ/AWQ 类方法的标准做法，比 per-tensor 精度高很多，比 per-channel 存储开销可控；
- **激活（A8）**：**Per-token quantization**（也叫 dynamic per-tensor per-token），即每个 token 的激活向量独立计算 scale。因为不同 token 的激活范围差异大，per-token 比 static per-tensor 精度好很多。

**在 OPPO 的经验（FP16 → INT8）：**

- 权重用 **Per-channel**（每个 output channel 一个 scale），这是 PTQ 的标准做法；
- 激活用 **Per-tensor dynamic**（运行时统计 min/max）；
- 还尝试过 per-group（group=64）来提升精度敏感层（如 Attention 的 QKV projection）的量化质量。

**为什么 per-group 是当前主流：** per-tensor 精度损失大（outlier 主导 scale），per-channel 对激活不适用（channel 维度是动态的），per-group 是精度和硬件效率的折中。

## Q12 对微调有了解吗？Agent 微调用了哪些方法？有用强化学习吗？

**微调经验：**

- 在 3GPP 文档分类项目中，对 BERT/GPT-2/RoBERTa 做过 SFT（Supervised Fine-Tuning），使用标准的 cross-entropy loss + AdamW + cosine scheduler；
- 了解 LoRA/QLoRA 等参数高效微调方法，理解 adapter 的原理（低秩分解插入 W = W₀ + BA）。

**Agent 微调方法（了解层面）：**

- **SFT 阶段**：使用高质量的 tool-calling/function-calling 数据做 instruction tuning，教模型学会"何时调用工具、如何格式化调用"；
- **RLHF/RLAIF**：在 SFT 基础上用强化学习对齐，reward model 评估模型的 tool use 质量（是否正确调用、参数是否合理、是否完成任务）；
- **强化学习方法**：主流用 PPO 或 GRPO（Group Relative Policy Optimization），最近 DeepSeek 等用的 GRPO 更稳定、不需要 critic model；
- **Agent 特有的 RL 信号**：除了 human preference，还可以用 environment feedback 作为 reward（如工具调用是否返回正确结果、任务是否完成）。

## Q13 强化学习微调的流程是什么？内嵌了哪些推理引擎？

**典型 RLHF/GRPO 流程：**

```text
1. SFT Model (初始策略)
   → 2. 采样生成 (Rollout/Generation)
   → 3. Reward 打分 (Reward Model / Rule-based)
   → 4. 策略更新 (PPO/GRPO loss 反向传播)
   → 5. 重复 2-4 直到收敛
```

**各阶段细节：**

1. **Generation（推理引擎）**：需要高效生成大量 rollout samples，这里内嵌推理引擎加速；
2. **Reward Scoring**：可以是 Reward Model（也需要推理）或 rule-based（如代码执行结果）；
3. **Training**：PPO/GRPO 的 actor-critic 更新，用 DeepSpeed/FSDP 做分布式训练。

**内嵌的推理引擎（主流框架）：**

- **vLLM**：OpenRLHF、veRL 等框架内嵌 vLLM 做 rollout generation，利用 PagedAttention + continuous batching 加速采样；
- **SGLang**：部分新框架开始集成 SGLang 替代 vLLM（RadixAttention 对 RLHF 中的重复 prefix 有天然优势）；
- **TensorRT-LLM**：NeMo-Aligner 使用 TRT-LLM 做推理加速；
- **DeepSpeed-Inference**：DeepSpeed-Chat 自带的推理模块。

**为什么需要内嵌推理引擎：** RLHF 训练中 generation 占了 70%+ 的时间（需要对每个 prompt 生成多条 response），如果用 naive HF generate 太慢，必须用 KV Cache + batching 优化的推理引擎。
