# 二、基础原理部分

## Q2 Transformer 的流程，有什么地方做得不好

### 前向流程（一层 Decoder Block，Pre-LN 结构）

以主流的 **Decoder-only + Pre-Norm** 架构（GPT / LLaMA / Qwen）为例，单个 block 内：

```
x
├─ RMSNorm ─→ Multi-Head Attention ─→ (+) 残差
│                                        │
├─ RMSNorm ─→ FFN(MLP / MoE) ──────────→ (+) 残差
                                         │
                                        out → 下一层
```

**逐步拆解**：

1. **输入**：token → embedding（`[batch, seq, d_model]`），加上位置编码（现代模型用 **RoPE** 旋转位置编码，加在 Q/K 上而非输入上）。
2. **归一化**：Pre-LN，先过 RMSNorm/LayerNorm 稳定分布。
3. **注意力**：
   - 线性投影出 Q、K、V：`Q=xWq, K=xWk, V=xWv`
   - 打分：`scores = QKᵀ / √d_k`
   - 因果 mask（下三角，防止看到未来 token）
   - softmax → 加权求和：`attn = softmax(scores) · V`
   - 输出投影：`out = attn · Wo`
4. **残差相加** → 再归一化 → **FFN**（`FFN(x)=W₂·激活(W₁x)`，中间维度通常 4×d_model；MoE 则换成多个专家 + 路由）。
5. **残差相加** → 堆叠 N 层 → 最后一层输出过 LM Head（`× W_vocab`）→ softmax → 下一个 token 的概率分布。

### "有什么地方做得不好"（开放题，考认知深度）

| 缺陷 | 具体问题 | 对应的优化方向 |
| --- | --- | --- |
| **① 注意力 O(n²) 复杂度** | self-attention 的 `QKᵀ` 是 `seq×seq`，长序列时**计算和显存都平方级爆炸**；80K 上下文时注意力矩阵巨大 | FlashAttention（分块 + online softmax，IO 感知，不落 n² 中间矩阵）；稀疏/线性注意力 |
| **② KV Cache 显存膨胀** | decode 阶段每层每 token 都要缓存 K、V，**显存随 `层数×序列长×并发` 线性增长**，是长上下文/高并发的头号瓶颈 | MQA / **GQA**（多 query 共享 KV head，直接砍 KV 显存）；PagedAttention 分页管理；KV 量化 |
| **③ Decode 串行、memory-bound** | 自回归一次只出一个 token，**无法并行**；每步要把整个模型权重 + KV 从显存搬进计算单元，算力吃不满（算术强度低） | 投机解码（speculative decoding）、Medusa / EAGLE 多头；continuous batching 提利用率 |
| **④ 长度外推差** | 训练时见过的位置有限，超出后位置编码失效、效果骤降 | RoPE + NTK/YaRN 插值、位置内插，扩展上下文窗口 |
| **⑤ Softmax 注意力的"全连接"浪费** | 每个 token 对所有 token 都算权重，但真实依赖往往是局部的 | 滑动窗口注意力（Mistral SWA）、分组/分块注意力 |
| **⑥ Pre-LN 深层训练不稳 / 表示坍缩** | 残差路径方差累积，深层网络难训 | 残差缩放、DeepNorm、更好的初始化 |

> **答题策略**：先干净利落地把流程讲完，再挑 **①②③** 三个和推理系统强相关的缺陷重点讲，并**自然引到 FlashAttention / GQA / PagedAttention / 投机解码**——这样正好接住后面 Q4（KV）、Q7（PD 分离）的追问，显得体系化。

## Q3 大模型从输入到输出的流程

**开口版**：一条推理请求从用户文本到生成结果，走的是「**预处理 → Prefill → Decode → 后处理**」四段，中间 Prefill 和 Decode 是两个特性完全不同的阶段（这也是 PD 分离的根源）。

### 完整链路

```
用户文本
  │
  ▼
① Tokenizer（分词）：文本 → token id 序列（BPE/SentencePiece）
  │
  ▼
② Embedding：token id → 向量 [1, seq, d_model]（+ 位置编码 RoPE）
  │
  ▼
③ Prefill 阶段（并行处理整个 prompt）
  │   N 层 Decoder Block 一次性算完所有输入 token
  │   → 产出并写入 KV Cache
  │   → 最后一个位置过 LM Head → 采样出【第 1 个 token】
  │   ★ 决定 TTFT（Time To First Token）
  │   ★ compute-bound：大矩阵乘，算力打满
  │
  ▼
④ Decode 阶段（自回归，逐 token）
  │   loop:
  │     新 token → embedding → 过 N 层（复用已有 KV Cache，只算 1 个新 token 的 QKV）
  │     → LM Head → 采样 → 下一个 token
  │     直到遇到 EOS / 达到 max_tokens
  │   ★ 决定 TPOT（Time Per Output Token）
  │   ★ memory-bound：每步搬权重+KV，算力吃不满
  │
  ▼
⑤ Detokenizer（反分词）：token id 序列 → 文本，流式吐给用户
```

### 关键点（面试要讲的"为什么"）

- **Prefill 和 Decode 特性相反**：
  - Prefill：一次算 `seq_len` 个 token，**大 batch 的矩阵乘**，**compute-bound**，决定 **TTFT**。
  - Decode：一次只算 **1 个** token，**访存受限（memory-bound）**，决定 **TPOT / 吞吐**。
  - → 这正是 **Q7 PD 分离**的动机：两个阶段混在一起会互相干扰（prefill 的长计算会阻塞 decode 的低延迟需求）。
- **KV Cache 的作用**：decode 时前面 token 的 K、V 已经算过，缓存下来避免重复计算，把每步复杂度从 O(n²) 降到 O(n)，代价是显存（见 Q4）。
- **Continuous Batching**：不同请求长度不一，传统静态 batch 会被最长请求拖住。continuous batching 让已完成的请求立即退出、新请求随时插入，把 decode 阶段的 GPU 利用率拉满。
- **采样**：LM Head 输出 logits → 按 temperature / top-k / top-p 采样得到下一个 token（贪心是特例）。

## Q5 RMSNorm vs LayerNorm

**开口版**：两者都是归一化，**LayerNorm 同时做「减均值 + 除标准差」的 re-centering 和 re-scaling；RMSNorm 砍掉了减均值这一步，只用均方根（RMS）做 re-scaling**。结果就是 RMSNorm **计算更省、参数更少、速度更快**，效果基本持平，所以 LLaMA / Qwen / Mistral 这些现代大模型几乎都用 RMSNorm。

### 公式对比

**LayerNorm**：

$$
\text{LayerNorm}(x) = \gamma \odot \frac{x - \mu}{\sqrt{\sigma^2 + \epsilon}} + \beta
$$

其中 $\mu = \frac{1}{d}\sum_i x_i$（均值），$\sigma^2 = \frac{1}{d}\sum_i (x_i-\mu)^2$（方差），$\gamma$ 是缩放参数、$\beta$ 是偏移参数。

**RMSNorm**：

$$
\text{RMSNorm}(x) = \gamma \odot \frac{x}{\text{RMS}(x)}, \quad \text{RMS}(x) = \sqrt{\frac{1}{d}\sum_i x_i^2 + \epsilon}
$$

没有减均值、没有 $\beta$ 偏移项。

### 对比表

| 维度 | LayerNorm | RMSNorm |
| --- | --- | --- |
| **减均值（re-centering）** | ✅ 有 | ❌ 无 |
| **除标准差/均方根（re-scaling）** | ✅ 除 $\sqrt{\sigma^2+\epsilon}$ | ✅ 除 $\text{RMS}(x)$ |
| **参数** | $\gamma$（scale）+ $\beta$（bias），两组 | 只有 $\gamma$，一组 |
| **计算量** | 需算均值 + 方差（两次遍历/规约） | 只算平方和（一次规约），**约省一半规约开销** |
| **平移不变性** | 有（对输入整体平移不敏感） | 无（但因为不减均值，实现更简单） |
| **速度** | 较慢 | **更快**（kernel 更简单，访存更少） |
| **代表模型** | BERT、GPT-2、原始 Transformer | **LLaMA、Qwen、Mistral、Gemma** 等主流 LLM |

### 为什么 RMSNorm 够用（核心洞察）

原论文（Zhang & Sennrich, 2019）的假设是：**LayerNorm 起效的关键是 re-scaling（把向量长度归一化），而不是 re-centering（减均值）**。既然减均值贡献不大，就可以砍掉，只保留 RMS 缩放——**省掉了均值计算和 bias 参数，性能几乎不掉，但推理/训练更快**。在动辄几十上百层的大模型里，这点节省被放大得很可观。

> 补充：还有 **Pre-Norm vs Post-Norm** 的位置问题——现代 LLM 用 **Pre-Norm**（归一化放在子层输入前、残差分支内），训练更稳定、更容易加深；原始 Transformer 是 Post-Norm。面试如果追问可以带一句。

## Q9 Attention 里的 Q 是怎么算出来的

**开口版**：Q（Query）不是凭空来的，它就是**当前层的输入 hidden state 经过一个可学习的线性投影（矩阵乘法）得到的**——`Q = X · Wq`。K、V 同理，只是各自用不同的权重矩阵。

### 具体计算

设某一层输入 $X \in \mathbb{R}^{[seq,\ d_{model}]}$：

$$
Q = X W_q, \quad K = X W_k, \quad V = X W_v
$$

- $W_q, W_k, W_v$ 是**可学习参数矩阵**，训练时学出来。
- 在 **MHA（多头注意力）** 里，$W_q$ 会被切成 $h$ 个头，每个头 $d_k = d_{model}/h$ 维；等价于把 Q reshape 成 `[seq, num_heads, head_dim]`。
- 在 **GQA / MQA** 里，K、V 的头数比 Q 少（多个 Q 头共享一组 KV 头），所以 $W_k, W_v$ 更小 → **KV Cache 更省显存**（呼应 Q2 缺陷②、Q4）。

### Q/K/V 的语义（面试常追问"为什么要分三个"）

| 角色 | 含义 | 类比 |
| --- | --- | --- |
| **Q（Query）** | 当前 token「**想找什么**」 | 检索时的查询词 |
| **K（Key）** | 每个 token「**能提供什么、可被匹配的标签**」 | 被检索文档的索引/key |
| **V（Value）** | 每个 token「**匹配上后实际要传递的信息**」 | 文档正文内容 |

注意力就是拿当前 token 的 **Q** 去和所有 token 的 **K** 做相似度（点积），softmax 归一化成权重，再用权重去加权聚合所有 token 的 **V**：

$$
\text{Attention}(Q,K,V) = \text{softmax}\!\left(\frac{QK^\top}{\sqrt{d_k}}\right)V
$$

- $\sqrt{d_k}$ 缩放：防止点积随维度变大而方差过大，把 softmax 推入梯度消失的饱和区。
- Decoder 里还要加**因果 mask**：把上三角（未来 token）的 score 置 $-\infty$，保证自回归只能看到过去。

> **一句话记忆**：Q/K/V 都是同一个输入 X 乘三个不同权重矩阵投影出来的；Q 是「查询」，K 是「索引」，V 是「内容」，注意力 = 用 Q·K 算权重、加权求和 V。

# 三、KV Cache 与显存部分

## Q4 KV Cache Block 计算（block=64 / 100 token）

> 这是**当场算显存**的硬核题。先记死总公式，再套具体模型。

### ① 100 个 token 需要多少 block？

block 按 **token 数**切分，一个 block 装 `block_size` 个 token 的 KV。向上取整：

$$
\text{blocks} = \left\lceil \frac{100}{64} \right\rceil = \lceil 1.5625 \rceil = \boxed{2\ \text{个 block}}
$$

- 第 1 个 block 装满 64 token，第 2 个 block 只用了 36 token → **剩 28 个 token 的空间是内部碎片（浪费）**。
- 这就是分页管理的代价：**block 越大，最后一块的内部碎片越多**；block 越小，元数据/管理开销越大。vLLM 默认 `block_size=16` 就是在两者间取平衡（题设 64 偏大，碎片更明显）。

### ② block 按 token 切还是按字节切？

**按 token 切。** 一个 block = 固定 `block_size` 个 token 在**每一层、每个 KV head**上的 K 和 V 张量。所以一个 block 的字节数是**由模型结构 + block_size + dtype 决定**的，不是任意字节数。这也是 PagedAttention「像操作系统页表/虚拟内存那样管理显存」的核心——**页大小固定（token 数固定），没有外部碎片，只有最后一块的内部碎片**。

### ③ 一个 block 占多少显存？（总公式）

$$
\boxed{\text{每 block 字节} = 2 \times L \times H_{kv} \times d_{head} \times \text{block\_size} \times \text{dtype\_bytes}}
$$

- `2`：K 和 V 两份
- `L`：层数（num_layers）
- `H_kv`：KV head 数（GQA 下 < Q head 数）
- `d_head`：每个 head 的维度（head_dim）
- `block_size`：每 block 的 token 数（题设 = 64）
- `dtype_bytes`：KV Cache 精度（FP16/BF16 = 2，FP8 = 1）

**每 token 的 KV**（去掉 block_size）：$2 \times L \times H_{kv} \times d_{head} \times \text{dtype\_bytes}$

### ④ 代入具体模型算（拿 LLaMA-3-8B 举例）

参数：`L=32`，GQA `H_kv=8`，`d_head=128`，`dtype=FP16(2B)`，`block_size=64`。

**每 token KV**：
$$2 \times 32 \times 8 \times 128 \times 2 = 131072\ \text{B} = 128\ \text{KiB/token}$$

**每 block（64 token）**：
$$128\ \text{KiB} \times 64 = 8192\ \text{KiB} = \mathbf{8\ MiB/block}$$

**100 token 的实际数据量**：$128\ \text{KiB} \times 100 = 12.5\ \text{MiB}$
**但按 block 分配 = 2 × 8 MiB = 16 MiB**（多出的 3.5 MiB 就是最后一块的内部碎片）。

> **面试话术**：先报公式，再问一句"以 8B / GQA-8 / FP16 为例"，然后算出「**每 token 128 KiB、每 block 8 MiB、100 token 占 2 个 block = 16 MiB，其中约 3.5 MiB 是内部碎片**」。这样既展示了公式，又展示了对碎片/分页机制的理解。

### ⑤ 可能的延伸追问

| 追问 | 答法 |
| --- | --- |
| block_size 怎么选？ | 太小→元数据/页表开销大、kernel 效率低；太大→内部碎片多、显存浪费。vLLM 默认 16，长上下文/高并发场景可权衡调大 |
| 并发很多请求显存怎么估？ | 总 KV = 每 token KV × Σ(各请求 seq_len) × 并发数，再按 block 向上取整；据此反推能塞多少并发（bound line） |
| 怎么省 KV 显存？ | GQA/MQA 减 KV head、KV Cache 量化（FP8/INT8）、PagedAttention 减碎片、prefix caching 复用公共前缀、offload 到 CPU |
| MoE 模型的 KV 有区别吗？ | KV Cache 只跟 attention 的 `L / H_kv / d_head` 有关，**和 FFN 是不是 MoE 无关**；MoE 影响的是权重显存和专家路由，不影响 KV 公式 |

## Q6 部署模型显存不够怎么办

**开口版**：显存不够要**先分清是哪部分爆**——是**模型权重**装不下，还是**KV Cache**装不下，还是**激活值/中间态**峰值爆。三部分对症下药，从"改动小、见效快"到"改动大"排序上。

### 显存都花在哪

```
总显存 = 模型权重 + KV Cache + 激活值/中间态 + 框架/通信 buffer + 碎片
```

### 手段清单（按代价从小到大）

| 手段 | 原理 | 省哪块 | 代价/注意 |
| --- | --- | --- | --- |
| **① 权重量化** | FP16→INT8/W8A8、INT4/W4A8、GPTQ/AWQ/FP8 | **权重**（最直接，砍一半~3/4） | 精度略降；注意 `w4a8` 不支持开 EP |
| **② KV Cache 量化** | KV 存成 FP8/INT8 | **KV Cache** | 长上下文收益大，需验证精度 |
| **③ Tensor Parallel (TP)** | 单层权重切到多卡 | 权重 + 激活 | 卡间 AllReduce 通信频繁，需 NVLink/高速互联 |
| **④ Pipeline Parallel (PP)** | 按层切分到多卡 | 权重 | 有流水线气泡（bubble），micro-batch 缓解 |
| **⑤ Expert Parallel (EP)** | MoE 专家分到不同卡 | MoE 权重 | 需 All-to-All 路由通信 |
| **⑥ ZeRO / FSDP（offload）** | 优化器状态/梯度/参数分片，甚至 offload 到 CPU/NVMe | 训练态显存 | 推理主要用权重 offload |
| **⑦ CPU/NVMe Offload** | 把不常用的权重/KV 换出到主存或 SSD | 权重 / KV | 换来换去有 PCIe 带宽瓶颈，拖慢延迟 |
| **⑧ 减小 batch / max_seq_len** | 降低并发和最大上下文 | **KV Cache + 激活** | 牺牲吞吐/最大长度，最快见效的兜底 |
| **⑨ PagedAttention** | 分页管理 KV，消除外部碎片 | KV Cache（利用率） | vLLM/SGLang 默认已开 |
| **⑩ Prefix Caching** | 复用相同前缀（system prompt）的 KV | KV Cache | 编码 Agent 多轮对话场景收益极大 |
| **⑪ 激活重计算 / chunked prefill** | 用计算换显存，切块处理长 prompt | 激活峰值 | 略增计算 |
| **⑫ 换更大显存的卡 / 加卡** | 硬件解决 | 全部 | 成本最高 |

### 答题逻辑（推荐顺序）

1. **先定位**：`nvidia-smi` / 框架显存报告看是权重还是 KV 爆。
2. **推理场景优先级**：**量化（W8A8/W4A8）→ TP 多卡切分 → KV 量化 + PagedAttention + Prefix Caching → 减 batch/max_len 兜底 → offload/换卡**。
3. **结合 PTG**：我在 PPU 上就是靠 **W4A8/W8A8-INT8 量化 + PD 分离（把 KV 压力分到 D 池）+ Mooncake RDMA** 把 Kimi-K2.6 这种大 MoE 跑到 3P2D 生产配比的；显存看板盯 KV 利用率和命中率来反推并发上限（bound line）。

# 四、PD 分离部分

## Q7 为什么要 PD 分离？会不会反而更慢

### 为什么要 PD 分离（核心动机）

**一句话**：Prefill 和 Decode 是**两个特性完全相反**的阶段，混在一起跑（continuous batching 同池）会**互相干扰、谁都跑不好**，拆开后各自用最合适的硬件配比和调度策略，才能同时满足 TTFT 和 TPOT。

| 维度 | Prefill（P） | Decode（D） |
| --- | --- | --- |
| **一次处理** | 整个 prompt（seq_len 个 token） | 1 个 token |
| **瓶颈** | **compute-bound**（大矩阵乘，吃算力） | **memory-bound**（搬权重+KV，吃显存带宽） |
| **决定指标** | **TTFT**（首 token 延迟） | **TPOT**（每 token 延迟）/ 吞吐 |
| **理想资源** | 高算力 | 高显存容量/带宽 |

**混部的问题（为什么要拆）**：
- **Prefill 抢占 Decode**：一个长 prompt 的 prefill 是重计算，插进 batch 会**阻塞正在 decode 的请求**，导致其他用户的 TPOT 突然抖动（inter-token latency 尖刺）。
- **资源画像冲突**：PPU 这类**显存大、算力低**的卡，prefill 阶段算力是短板，decode 阶段显存是短板，同池没法两边都最优。
- **无法独立扩缩容**：长输入短输出的 workload（我的场景平均 input 80K+）需要**多配 P**；短输入长输出需要**多配 D**。混部就只能整体扩，浪费。

**PD 分离的收益**：
1. **各自独立调度/扩缩容**：P 池和 D 池按 workload 调配比（如 **3P2D**）。
2. **消除相互干扰**：decode 的 TPOT 更平稳，SLA 更好保。
3. **可用不同硬件/并行策略**：P 侧重算力（TP 小、batch 大），D 侧重大显存装 KV。
4. **KV Cache 分层**：P 算完把 KV 传给 D，D 专注自回归。

### 有没有可能 PD 分离反而更慢？（关键反问，一定要答"会"）

**会。** PD 分离不是银弹，以下情况**可能得不偿失甚至更慢**：

| 场景 | 为什么反而慢 |
| --- | --- |
| **① KV 传输开销 > 分离收益** | P 算完的 KV Cache 要**跨节点传到 D**。如果没有 RDMA / 高速网络，或传输没和计算 overlap，这段网络延迟直接加到 TTFT 上。短序列时 KV 小但传输的固定开销（建连、握手）占比高。 |
| **② 小模型 / 短序列** | prefill 本身很便宜，分离带来的调度、传输、两跳网络开销可能**超过**它省下的干扰，得不偿失。 |
| **③ 低 QPS / 请求量不足** | P 池和 D 池都填不满，**两边都有空闲**，整体利用率反而低于混部（混部能靠 continuous batching 把碎片填满）。 |
| **④ 配比失衡** | P:D 配比没标定好，一边排队一边空转。比如长输入场景 P 配少了 → P 成瓶颈 → TTFT 爆。 |
| **⑤ 多了一跳网络 + 序列化** | 请求要经过 P→D 的转发，多了序列化/反序列化和服务发现开销。 |

**结论话术**：
> PD 分离在**高并发、长上下文、对 TTFT 和 TPOT 都有硬 SLA**的生产场景收益最大；但在**低 QPS、小模型、短序列、或网络带宽不足（KV 传输没法 overlap）**的情况下，分离引入的传输和调度开销可能让它**反而更慢**。所以要不要上 PD 分离，得看 workload 画像和网络能力——我在 PTG 上是**长输入短输出 + 80K 上下文 + RDMA 传输**，分离收益明确，才上了 3P2D。

详见 [[Infra/PD分离]]。

## Q8 D 节点会影响 TTFT 吗

**开口版（直接给结论）**：**会。** 很多人误以为 TTFT 只由 Prefill 决定，但在 PD 分离架构下，**首 token 实际是在 D 节点上生成的**，所以 TTFT 是一条**贯穿 P→传输→D 的完整链路**，D 节点的状态（排队、传输、首个 decode step）都会影响 TTFT。

### TTFT 在 PD 分离下的完整拆解

```
TTFT = 在 P 池排队时间
     + Prefill 计算时间（P 节点，compute-bound）
     + KV Cache 从 P 传到 D 的时间（网络/RDMA）★
     + 在 D 池排队时间 ★
     + D 节点执行【第一个 decode step】的时间 ★
```

**标 ★ 的三项都和 D 节点直接相关**：

| 影响因素 | 怎么拖慢 TTFT |
| --- | --- |
| **KV 传输（P→D）** | KV Cache 要跨节点搬到 D。网络带宽不足 / 没和 prefill overlap / 建连开销大 → 这段时间**全加在 TTFT 上**。这是 PD 分离 TTFT 的主要额外成本（也正是 Q7"会不会更慢"的核心）。 |
| **D 池排队** | 如果 D 节点都在忙（decode 请求排满），新请求的 KV 传过来了也得**等 D 有空**才能开始第一个 decode step → TTFT 变长。 |
| **D 的首个 decode step** | 首 token 是 D 上跑第一步 decode 出来的，D 的负载/batch 大小/显存带宽直接决定这一步多快。 |

### 对比：混部 vs PD 分离的 TTFT

- **混部（同池）**：没有 KV 跨节点传输，TTFT = 排队 + prefill + 首个 decode step，链路短，但 prefill 会被别的 decode 干扰、抖动大。
- **PD 分离**：多了 **KV 传输 + D 池排队**两段，**如果这两段没优化好，TTFT 反而可能比混部更高**；但换来的是 decode 阶段 TPOT 更稳、吞吐更高。

### 优化方向（怎么让 D 不拖累 TTFT）

1. **KV 传输与 Prefill 计算 overlap**：边算边传（layer-wise streaming），别等 prefill 全算完再传。
2. **RDMA / Mooncake Transfer Engine**：kernel bypass 直达显存，压低传输延迟（我在 PTG 用 8 张 `mlx5_bond` 并行传）。
3. **P:D 配比标定 + 动态调度**：避免 D 池排队成为 TTFT 瓶颈；用 Dynamo 这类做动态负载均衡。
4. **D 池预留 headroom**：别让 D 打满到无法及时接收新请求的首个 decode step。

**结论话术**：
> TTFT 不是"prefill 结束就结束"。在 PD 分离下，首 token 由 D 节点产出，所以 **TTFT = P 排队 + prefill + KV 传输 + D 排队 + D 首个 decode step**，D 节点通过"KV 传输"和"D 池排队/首步 decode"两段实打实地影响 TTFT。这也是为什么 PD 分离必须配 RDMA + 传输 overlap + 合理配比，否则 TTFT 会被 D 侧拖慢。

# 五、手撕部分

## Q10 手撕：数组中第 k 个最大元素（LC215）

> 题目：给定整数数组 `nums` 和整数 `k`，返回数组中**第 k 个最大**的元素。要求尽量优于 O(n log n) 排序。
> 关联背诵手册：[[Leetcode/CodeTop手撕40题背诵手册]]

### 解法一：快速选择 Quickselect（最优，平均 O(n)）★ 面试首选

基于快排 partition：每次 partition 后，基准元素落到它最终排序的位置。**只递归基准所在的那一侧**，不像快排两边都递归 → 平均 O(n)。

```python
import random

def findKthLargest(nums: list[int], k: int) -> int:
    # 第 k 大 = 升序排序后下标 len(nums)-k 的元素
    target = len(nums) - k

    def partition(left: int, right: int) -> int:
        # 随机选 pivot，避免有序数组退化到 O(n^2)
        rand_idx = random.randint(left, right)
        nums[rand_idx], nums[right] = nums[right], nums[rand_idx]
        pivot = nums[right]
        i = left  # i 左边都是 < pivot 的元素
        for j in range(left, right):
            if nums[j] < pivot:
                nums[i], nums[j] = nums[j], nums[i]
                i += 1
        nums[i], nums[right] = nums[right], nums[i]  # pivot 归位
        return i  # pivot 的最终下标

    left, right = 0, len(nums) - 1
    while True:
        p = partition(left, right)
        if p == target:
            return nums[p]
        elif p < target:      # 目标在右半区
            left = p + 1
        else:                 # 目标在左半区
            right = p - 1
```

- **时间复杂度**：平均 **O(n)**（n + n/2 + n/4 + ... ≈ 2n）；最坏 O(n²)，**用随机 pivot 规避**。
- **空间复杂度**：O(1)（原地 partition，迭代写法无递归栈）。
- **必讲点**：① 第 k 大 → 目标下标是 `len-k`（升序）；② **随机化 pivot** 防止有序数组退化；③ 只递归一侧是它比快排快的原因。

### 解法二：小顶堆 Min-Heap（O(n log k)，兜底/海量数据流场景）

维护一个**大小为 k 的小顶堆**，堆顶始终是"当前 k 个最大里最小的那个"。遍历完，堆顶就是第 k 大。

```python
import heapq

def findKthLargest(nums: list[int], k: int) -> int:
    heap = []  # 小顶堆，容量维持 k
    for x in nums:
        heapq.heappush(heap, x)
        if len(heap) > k:
            heapq.heappop(heap)  # 弹掉最小的，只保留 k 个最大
    return heap[0]  # 堆顶 = 第 k 大
```

- **时间复杂度**：O(n log k)；**空间**：O(k)。
- **适用**：**数据流 / 海量数据装不进内存**时（k 远小于 n，堆只占 k），或面试官明确不让改原数组、要 online 处理。
- **为什么是小顶堆不是大顶堆**：要第 k 大，就用小顶堆留住"最大的 k 个"，堆顶（这 k 个里最小的）即答案；建堆 O(k)、每次调整 O(log k)。

### 两种解法怎么选（面试话术）

> "如果是一次性数组、追求最优时间，我用**快速选择，平均 O(n)、原地 O(1) 空间**，注意随机化 pivot 防退化；如果是**数据流或数据量远超内存**、k 又很小，我用**大小为 k 的小顶堆，O(n log k) 但只占 O(k) 空间**、天然支持 online。"
