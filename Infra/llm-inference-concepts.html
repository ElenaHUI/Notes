LLM 推理核心概念图解

从一次请求的旅程出发：请求怎么被路由（Dynamo）→ 在哪里算（PD 分离）→ 算什么（KV Cache）→ 怎么高效地算（Continuous Batching / PagedAttention / GQA / FlashAttention）

1. KV Cache 一切的基础

先讲 KV Cache，因为后面所有概念都围绕它展开。Transformer 生成文字是「自回归」的：每生成一个新 token，都要回头看前面所有 token。如果每次都重新计算前面 token 的中间结果，计算量会随长度平方爆炸。KV Cache 就是把算过的结果存下来复用。

一句话：每个 token 在每一层 Transformer 里都会产生一对 Key 和 Value 向量，KV Cache 就是把这些向量按「层 × 头 × 序列位置」存在显存里。Decode 阶段每步只需计算新 token 的 K/V 并追加进缓存，再读缓存做 attention。代价是：缓存随序列长度线性增长，长上下文时能吃掉几十 GB 显存——这正是后面 PagedAttention、GQA、PD 分离要解决的问题。

2. Continuous Batching 调度层：怎么凑批

GPU 一次处理一个请求太浪费，要凑成 batch 一起算。问题是：batch 里每个请求的输出长度不一样，怎么凑？

一句话：不再以「整个 batch」为单位进出，而是以「每一步迭代」为单位动态组 batch——谁生成完了谁退出，新请求随时插入。它让 GPU 几乎永远满载，是现代推理引擎吞吐量的第一功臣。但它也带来一个新问题：batch 里同时有很多请求，每个请求的 KV Cache 大小还不一样、还在不断增长，显存怎么管？——这就是 PagedAttention。

3. PagedAttention 显存层：KV Cache 怎么存

朴素做法是给每个请求按「可能的最大长度」预分配一整块连续显存。结果：大量显存被预留但没用上（内部碎片），请求长度不一又留下空隙（外部碎片），实测浪费率可达 60~80%。vLLM 的 PagedAttention 借用了操作系统「虚拟内存分页」的思想。

一句话：把 KV Cache 切成固定大小的块，用一张「块表」记录逻辑块到物理块的映射，物理上不必连续。好处：显存浪费降到 4% 以内，同样的卡能并发更多请求；请求结束后块立即回收复用；共享同一 system prompt 的请求可以直接共享物理块。这是 vLLM 的立身之本，也是你简历里「KV Cache 占用率」这个调度指标能精确到块的原因。

4. GQA 模型层：让 KV Cache 本身变小

一句话：GQA 让一组 Query 头共享同一份 Key/Value，在「MHA 精度好但缓存大」和「MQA 缓存小但精度差」之间取了平衡点，KV Cache 体积和 Decode 带宽需求直接缩小数倍。它和 PagedAttention 是互补的：一个让缓存天生就小，一个让存储方式不浪费。

5. FlashAttention 算子层：让 attention 算得快

前面都在讲「存」，FlashAttention 解决的是「算」。GPU 里显存（HBM）很大但慢，片上 SRAM 极快但只有几十 MB。标准 attention 的中间矩阵（seq_len × seq_len 的注意力分数）要反复在 HBM 上读写，瓶颈不在算力而在搬数据。

一句话：FlashAttention 的精髓是「分块（tiling）+ 在线 softmax」——数学上严格等价于标准 attention，但通过把计算切成能装进 SRAM 的小块、边算边累加 softmax，让巨大的中间分数矩阵永远不写回慢速显存。它和 GQA 是正交的优化：GQA 减少要处理的数据量，FlashAttention 减少数据搬运的次数。

6. PD 分离 部署层：Prefill 和 Decode 分家

前面四招都在单节点内挖潜。PD 分离（Prefill-Decode Disaggregation）则是在集群层面做分工：既然 Prefill 是算力密集、Decode 是带宽密集，干脆让它们跑在不同的机器上。

一句话：把「算 prompt」和「吐字」拆成两个资源池独立伸缩，中间用 RDMA 高速搬运 KV Cache 衔接。Prefill 池可以毫无顾忌地塞大 batch 压榨算力（不怕影响别人吐字），Decode 池可以稳定跑大 batch 匀速生成（不怕被长 prompt 打断）。代价是多了 KV 传输和跨节点协调的复杂度——你简历里 RDMA 吞吐瓶颈、FA3 兼容、配比压测，全是在填这个代价。

7. NVIDIA Dynamo 编排层：整个集群的大脑

PD 分离之后，集群里有一堆 Prefill worker、一堆 Decode worker，请求进来发给谁？KV 传给谁？谁该扩容？这些决策需要一个统一的编排层，这就是 Dynamo 的角色——对比之下，之前的 Kong 只是个只会按 hash 转发的「传话筒」。

一句话：Dynamo 是 PD 分离集群的「大脑」：Router 负责把请求动态分给最闲的 Prefill，Planner 负责盯着全局负载决定 KV 往哪传、P:D 比例怎么调，NIXL 负责高效搬运 KV 并管理多层缓存。它把 PD 分离从「手工搭的固定配置」升级成「能自我调节的弹性系统」——这正是你们从 Kong 迁到 Dynamo 的核心价值：路由从静态变动态，部署从固定配比变 Pod 级弹性。

七个概念串成一条线：KV Cache 是核心数据结构 → Continuous Batching 决定怎么凑请求 → PagedAttention 决定缓存怎么存 → GQA 让缓存变小 → FlashAttention 让计算变快 → PD 分离把两类负载拆到集群层面 → Dynamo 统筹整个集群。
