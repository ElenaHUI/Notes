# 1.worker重名问题排查说明

## 一、现象

Grafana 面板 **Per-Worker Active Decode Blocks**（数据源指标：`dynamo_frontend_worker_active_decode_blocks`）出现以下异常表现：
![[Pasted image 20260807173631.png]]

1. **图例重名**：图例共 6 条，但只有 2 个不同的 worker ID（`...421`、`...437`），每个 ID 各出现 3 次，图例文本完全相同，无法区分。
2. **曲线重叠**：重名的多条曲线走势几乎一致、在图上重叠，Tooltip 中数值**接近但不完全相同**（如 40.0 / 39.0）。

## 二、排查过程

- **查看面板 JSON**：发现查询为裸指标名，无聚合；图例模板只使用 `worker_id / dp_rank / worker_type / instance` 四个标签：
    
    ```
    worker={{worker_id}} | dp={{dp_rank}} | type={{worker_type}} | frontend={{instance}}
    ```
    

- **查看完整原始序列标签**：在 Prometheus 中查询该指标，发现实际只有 2 个真实 worker（同一 pod `dynamo-frontend-69c858c89b-7pn58` 内），但每个 worker 存在 2~3 条序列，差异仅在图例未展示的标签上：`endpoint`、`job`、`service`。

![[Pasted image 20260807174740.png]]
2. **验证抓取频率**：执行
    
    ```
    count_over_time(dynamo_frontend_worker_active_decode_blocks{worker_id="7042398185669850437"}[5m])
    ```
    
![[Pasted image 20260807173829.png|806]]
结果显示各序列样本数分别为 ≈60、≈60、≈20，对应抓取间隔 **5s / 5s / 15s**。

## 三、根因

**同一个 frontend pod 被 3 个不同的 ServiceMonitor（scrape 配置）重复抓取。**

|抓取源|endpoint 标签|job 标签|抓取间隔|
|---|---|---|---|
|Dynamo 自带 ServiceMonitor|`http`|`dynamo-system/dynamo-frontend`|5s|
|模型部署生成的 ServiceMonitor|`deeplseek-v4-flash`|`dynamo-system/dynamo-frontend`|5s|
|第三个 ServiceMonitor|`dynamo-frontend`|`dynamo-frontend`|15s|

三个抓取源的 selector 都匹配到了 frontend pod，于是同一份指标数据被采集 3 份存入 Prometheus，仅 `job`/`endpoint`/`service` 标签不同。由此产生三个后果：

- **图例重名**：图例模板恰好不含这三个区分标签 → 6 条序列只显示出 2 个名字；
- **曲线不完全重合**：三种抓取频率和相位不同，对快速变化的 gauge 指标（active decode blocks 随请求进出实时波动）在不同瞬间采样，瞬时值存在偏差，并非计算错误；
- **聚合重复计数**：`sum()` 会把同一 worker 的数据累加 2~3 倍，告警和容量统计失真。

## 四、解决方案

### 方案 A：面板层去重（立即生效，零风险）

修改 Grafana 面板查询，按业务维度聚合：

```
max by (worker_id, dp_rank, worker_type, instance) (dynamo_frontend_worker_active_decode_blocks)
```

由于重复序列来自同一数据源，`max` / `min` / `avg` 均可。此方案解决图例重名和面板重复计数问题，但 Prometheus 侧的重复存储仍然存在。

# 2.Grafana "Component Throughput" 面板图例重复问题排查说明

## 一、现象

Grafana 面板 **Component Throughput (bytes/sec)** 出现以下表现：

![[Pasted image 20260807182718.png]]
1. **图例重名**：图例共 4 条，但只有两个名字——`Response bytes` 出现 2 次（绿、黄），`Request bytes` 出现 2 次（蓝、橙），完全无法区分。
2. 曲线本身正常（有波动、有峰值），说明数据在，只是标识不清。

## 二、排查过程

1. **查看面板查询**（Query inspector → Query 标签页），得到两个查询目标：
    
    ```
    A: rate(dynamo_component_response_bytes_total{dynamo_endpoint="generate", model="DeepSeek-V4-Flash"}[1m0s])
    B: rate(dynamo_component_request_bytes_total{dynamo_endpoint="generate", model="DeepSeek-V4-Flash"}[1m0s])
    ```
    
    两个查询均为裸指标 + `rate()`，无聚合；legendFormat 写死为固定字符串。
2. **在 Prometheus 中验证序列数量与标签**：

```
    rate(dynamo_component_request_bytes_total{dynamo_endpoint="generate", model="DeepSeek-V4-Flash"}[5m])
```
    
返回 2 条序列（`Result series: 2`），标签对比：
![[Pasted image 20260807182818.png]]

## 三、原因

与之前 "Per-Worker Active Decode Blocks" 的重复抓取问题**不同**，本次是纯粹的**图例配置问题**：

- 该模型部署了 **2 个真实的 vLLM worker 副本**（pod、IP、worker_id 均不同），每个 worker 各产生一条序列，数据本身完全正确；
- 该指标的抓取源只有一个（`endpoint="system"`），**不存在重复抓取**；
- 图例重名的唯一原因：两个查询的 **legendFormat 被写死为 `Request bytes` / `Response bytes`**，没有包含 `{{worker_id}}`、`{{instance}}` 等区分变量，导致 2 条不同序列共用同一个名字。

**附带发现**：查询的 `rate` 窗口为 `[1m]`，而该指标抓取间隔为 15s，窗口偏小（理想应 ≥ 4 倍抓取间隔），可能导致曲线偶发断点或抖动。

## 四、解决办法

本次**无需聚合**（两条线各有业务含义，且无重复计数风险），只需修改面板配置：
![[Pasted image 20260807183405.png]]

1. 面板 **Edit → Query**，修改图例格式：
    - 查询 A（response）：`Response bytes | worker={{worker_id}}`
    - 查询 B（request）：`Request bytes | worker={{worker_id}}`  
        （也可用 `{{pod}}` 或 `{{instance}}`，视可读性偏好）
